# ShopCare · 电商客服工单智能处理平台

把"用户反馈"变成"可派单的结构化决策": 一条工单进来, 一次性给出
**多标签分类 + 情感极性 + 优先级/SLA + 责任部门 + 建议回复草稿 + 是否需要人工复核**。

技术路线上做了三套**可自由切换的对照模型**(随机森林 / FastText / BERT+LoRA),
外加两档升级路径(自动升级 LLM 兜底 / LLM 直连), 便于直接对比"传统方法到什么程度、
深度模型值不值得上"。这也是本项目作为教学/答辩材料时最有说服力的部分。

> 项目名与包名(ShopCare)是占位用的, 可以整体替换, 不影响功能。

## 一、快速开始

```bash
# 1) 依赖(服务侧最小集; 模型侧按需装)
pip install -r backend/requirements.txt

# 2) 数据(仓库里已含 train 10 万 / dev·test 各 8 千的演示语料, 需要重新生成时执行)
python tools/build_dataset_v2.py          # 540 条模板 + 家族分组切分 + 槽位隔离, 约 4 秒
python tools/check_dataset.py             # 格式体检
# 注意: tools/generate_ticket_data.py 是旧版生成器, 会产出模板级泄漏的语料, 不要再用于出指标

# 3) 训练对照组(任选; 仓库里 02/03 的模型产物已经训练好)
python 02-rf/rf_train.py
python 03-fasttext/ft_train.py
# BERT 需要先把 bert-base-chinese 放到 04-bert/bert-base-chinese/, 再:
python 04-bert/train_bert.py

# 4) 启动后端 + 前端
python backend/main.py
# 浏览器打开 http://127.0.0.1:8000/app   接口文档 /docs
```

**没有任何外部服务也能跑起来**: MySQL / Redis 连不上时, 后端会自动降级到内存存储与
进程内限流, 接口和页面全部可用(数据重启即丢), 降级情况会如实显示在 `/health` 与页面的
「系统状态」里。**唯一需要你自备的**是 BERT 的本地预训练模型目录(见下文)。

登录: 首次启动自动创建管理员 `admin / admin123`(改 `backend/.env` 可覆盖), 也可以直接在
登录页注册普通账号。

## 四、三套对照模型: 实测对比

在同一份演示语料(train 100000 / dev 8000 / test 8000)上的结果:

| | 随机森林 (TF-IDF) | FastText | BERT + LoRA |
|---|---|---|---|
| 产物 | `02-rf/save_models/rf_tfidf.joblib` | `03-fasttext/save_models/*.bin` | `04-bert/save_models/*.pt` |
| 体积 | 15.6 MB | 19.6 MB | 视 LoRA 配置, 通常 10~60 MB |
| 训练耗时 | 94 s | 56 s | 分钟级(GPU); CPU 上数小时 |
| 测试集 Micro-F1 | **0.653** | **0.760** | 0.918 ※ |
| 测试集 Macro-F1 | 0.654 | 0.783 | 0.928 ※ |
| 子集准确率(整单全对) | 0.365 | 0.469 | 0.837 ※ |
| 平均置信度 | 0.595 | 0.679 | 0.936 ※ |
| 自动分流率 / 拒识率 | 87.9% / 12.1% | 83.5% / 16.5% | 89.9% / 10.1% ※ |
| 自动分流 Micro-F1 | 0.682 | 0.800 | 未记录 |
| 标定阈值(单标签/全局) | 0.35 / 0.39 | 0.30 / 0.454 | 0.2 / 未记录 ※ |
| 概率校准 ECE(校准前→后) | 0.197 → **0.020** | 0.054 → **0.016** | 未记录 |
| 语料外新说法 | 容易漏判/拒识 | 较好 | 最好 |

> ※ **BERT 那一列来自一次云端 GPU 训练**(`04-bert/result/test_metrics.json`, 2026-09-22),
> 语料已经是去掉泄漏后的版本, 指标有效; 它也**已经做了**概率校准(Platt)和 dev 上的双阈值
> 标定, 所以口径与另两列一致。三点需要说明:
>
> 1. 该轮的 `epochs=5`(GPU 上取的轮数)。本机 CPU 跑同样的 5 轮要约 20 小时, 所以
>    `04-bert/config.py` 的注释按 CPU 成本建议降到 2 轮 —— **本机重训的数字会低于这一列**,
>    两者不可混用。
> 2. 产物里只记了标定出的单标签阈值 0.2, 全局阈值与 ECE 没有落盘, 所以那两格是"未记录",
>    不是"没做"。
> 3. 它的 `train_loss` 在第 5 轮已掉到 0.0001 而 dev Micro-F1 在 0.92 附近震荡(见
>    `04-bert/result/train_log.json`), **BERT 自身也存在过拟合**, 这与语料是合成模板有关。

> **"平均置信度"只有做了校准的这两个模型才有意义**(见下文 4.1)。校准前 RF 的原始输出
> 挤在 0.30 附近、FastText 有 7.4% 的标签直接顶到 1.000 —— 同一件事, 一个像是模型没把握、
> 一个像是数据泄漏, 根本没法放在一张表里。不过两者现在用的是**不同的校准方法**
> (RF 等频分箱 / FastText Platt), 所以这两个数字是"各自校准后都表示经验正确率",
> 而不是"同一把尺子上量出来的"。

> **表里的拒识率是 test 上的实测值, 与 15% 的业务目标略有出入, 原因不同**: FastText 在 dev
> 上标定到 15.0%(正好顶到约束上限), test 上漂到 16.5% —— 这 1.5 个点是**标定集与评测集的
> 难度差**: 两个 split 各只有 108 个模板家族, 随机一分难度就会有差异, 实测 dev 上有 96.6%
> 的工单能激活标签, test 上只有 91.3%。RF 的 12.1% 则**不是漂移, 是主动选择** —— 它在 dev
> 上把阈值定在 11.5% 时自动分流 Micro-F1 最高(0.722), 强行把拒识率顶到 15% 反而要让出
> 准确度, 所以没顶到上限(dev 11.5% → test 12.1%, 只漂了 0.6 个点)。
> 真实上线应当用线上数据**持续**重新标定, 而不是一次标定用到底。

> **这张表是可比较的, 因为语料已经修掉了模板级泄漏。**
>
> 早期版本的演示语料有个致命问题: 整句查重是 0, 但 **test 里 96.6% 的子句能在 train 中
> 原样找到** —— 每条测试文本只是几千条模板子句的重新排列组合, 模型学到的其实是
> 「子句 → 标签」的查表规则, 所以 RF / BERT 都是 Micro-F1 = 1.000, 指标没有区分度。
>
> 现在语料由 `tools/build_dataset_v2.py` 重建(540 条模板 + 家族分组切分 + 槽位隔离),
> **test 子句在 train 中原样出现的比例是 0.0000%**。所以上表的数字有真实区分度:
> 纯字面特征的 RF 明显弱于带 n-gram 语义的 FastText, 这正是"要不要上更重的模型"
> 这个问题该有的样子。校验方法与完整报告见 `01-data/split_manifest.json`。

### 4.1 概率校准:为什么两张表的置信度能放在一起比

两个模型的**原始输出都不是"可信度"**, 但错的方向正好相反。同一条工单
「发票开错了, 抬头写成公司旧名字, 能重开吗」:

| | 校准前 | 校准后 | 校准后实际含义 |
|---|---|---|---|
| `02-rf` | invoice = 0.605 | invoice = **0.912** | "大约 91% 的把握是发票问题" |
| `03-fasttext` | invoice = **1.000** | invoice = **0.890** | "大约 89% 的把握是发票问题" |

两个模型**标签都判对了**, 但校准前一个显示 60%(像是模型没把握)、一个显示 100%
(像是数据泄漏)。这不是个例, 在 test 上按原始分数分档统计就一目了然:

`02-rf` 的原始输出 —— 整段只有 `[0.041, 0.799]`, 中位数 0.302, **没有任何一个 ≥0.999**:

| 原始分档 | 标签数 | 它声称 | 实际命中 | 偏差方向 |
|---|---|---|---|---|
| `[0.70, 0.81)` | 38 | 0.718 | 1.000 | 保守 |
| `[0.60, 0.70)` | 262 | 0.624 | 0.989 | 保守 |
| `[0.50, 0.60)` | 3004 | 0.542 | 0.767 | 略保守 |
| `[0.30, 0.50)` | 33605 | 0.363 | 0.245 | **系统性高估** |
| `[0.00, 0.30)` | 35091 | 0.259 | 0.026 | **严重高估** |

`03-fasttext` 的原始输出 —— **7.40% 的标签概率正好顶到 1.000**:

| 原始分档 | 标签数 | 它声称 | 实际命中 | 偏差方向 |
|---|---|---|---|---|
| `[0.999, 1.001)` | 5329 | 1.000 | 0.942 | 略高估 |
| `[0.90, 0.999)` | 3662 | 0.971 | 0.671 | **严重高估** |
| `[0.80, 0.90)` | 828 | 0.854 | 0.594 | **严重高估** |
| `[0.50, 0.80)` | 1315 | 0.666 | 0.543 | 高估 |
| `[0.01, 0.50)` | 5934 | 0.116 | 0.255 | 低估 |

原因是两者的概率来自完全不同的机制:

- RF 的概率是 300 棵树在叶子上的投票比例, 天然被压向中间 —— 它**永远不会给出 1.0**,
  但低分段又高估得离谱(说 0.259, 实际只有 0.026), 整段 0.04~0.80 里几乎没有一处
  对得上;
- FastText 用 ova(每标签一个独立 sigmoid), 在 10 万条语料上训练 25 轮后会**饱和**,
  高分段被直接推到 1.000, 而它说 0.971 的那一档只说对了 67.1%。

两个数字都不可读, 而且**不可比**: 全局阈值 0.5 对 RF 和 FastText 根本不是同一件事。

**做法**: `tools/prob_calibration.py` 在 **dev** 上为每个标签单独拟合一个单调映射,
训练与推理两端都过一遍。单调保证**不改变排序**, 所以 Micro-F1 不是靠校准"调"上去的;
变的是"概率"这个数字本身的含义。test 不参与拟合, 指标依然干净。**两个模型用了不同的
校准方法**, 理由见下。

校准带来的收益(在 test 上实测):

| | ECE 校准前 | ECE 校准后 | 平均置信度 | 预测标签数 vs 真实 |
|---|---|---|---|---|
| `02-rf` | 0.197 | **0.020** | 0.595 | 1.46 vs 1.47 |
| `03-fasttext` | 0.054 | **0.016** | 0.679 | 1.59 vs 1.47 |

> **为什么 RF 用等频分箱, 而 FastText 用 Platt**: Platt 是对 `logit(p)` 做一维逻辑回归,
> 只有 2 个参数、平滑、不会输出正好 0/1 —— 对 FastText 这种"低分段全是 0、高分段饱和"
> 的分布很合适。RF 的分布却是**反过来的**: 有效信息全挤在 `[0.6, 0.8]` 这一小段
> (test 上 72000 个标签里只有 300 个落在这里), Platt 这条全局 sigmoid 要在整个区间上
> 拟合, 到高分段就变成**从个位数样本外推** —— dev 上它拟合出极陡的 `a≈7.19`, 把原始
> 0.482 外推成 0.9649; 而 dev 那段本身并不单调(logistics 在 `[0.55, 0.70)` 的命中率
> 0.50 反而**低于** `[0.50, 0.55)` 的 0.79), 那段基本是噪声。
>
> **等频分箱**按分位数切箱、每箱样本数相同, 尾部拿到的样本量和低分段一样多, 从根上
> 消除"个位数样本外推"; 落箱时范围外的输入**夹到端点箱**, 绝不外推。代价是输出变成
> 阶梯(同一箱内概率相同), 好处是**永远到不了 1.0** —— RF 校准后的最大输出是 0.963。
>
> **为什么不用保序回归(isotonic)**: 三种方法都试过。isotonic 在 dev 上的对数损失更低,
> 但那是**拟合过度**: dev 里恰好 100% 命中的分箱会被直接映射成 1.000, 换到 test 上就
> 成了新的过度自信(在 `02-rf` 上实测: isotonic 有 2.3% 的标签输出正好 1.0, 而 Platt
> 只有 0.3%)。而"显示 100%"正是这套系统要避免的东西。`auto` 模式会把三种都拟合一遍、
> 按 dev 对数损失挑选; 库的默认值是 `platt`, 只有 `02-rf` 显式改成了 `equal_freq`。

> **阈值为什么不是 0.5/0.8**: 两个模型都用 `--tune-threshold` 在 dev 上按业务目标
> (拒识率 ≤ 15% 前提下最大化自动分流 Micro-F1) 标定, 得到 RF `0.35 / 0.39`、
> FastText `0.30 / 0.454`。**注意这两个模型的校准方法不同, 所以阈值的跨模型可比性比
> "都用 Platt"时要弱一档** —— 可比的是语义(校准后的数字都表示经验正确率), 不是
> "同一把尺子上的同一个刻度"。要严格横向比较, 应当让两者用同一种校准方法重标一次。

### 4.2 长度先验:为什么「快递一直没到」曾被判成「无效与恶意」

这是语料重建过程中查出来的一个**隐蔽但很致命**的问题, 值得单独记一笔。

**现象**: 把几个最典型的物流说法单独喂给模型, 结果全是垃圾:

下表用的是 `03-fasttext`(它是当时受影响最明显的模型; 修复前的分数是未校准的原始输出,
修复后的是当前校准产物):

| 输入 | 修复前 | 修复后(现产物) |
|---|---|---|
| `物流` | **invalid 0.95** | 全部标签都很低, 最高 `invalid` 0.067(见下注) |
| `快递一直没到` (6 字) | **invalid 1.00** | **logistics 0.847** |
| `包裹一直没到` | 全标签 ≈ 0 | **logistics 0.847** |
| `东西还没发货` | 全标签 ≈ 0 | **logistics 0.847** |
| `我的快递一直没到` (8 字) | logistics 1.00 ✅ | logistics 0.847 ✅ |

第 5 行是关键线索:**只有它是对的**。区别只在长度 —— 8 字能认, 6 字就崩。

**根因**: 原来的语料里, 9 个标签中**只有 `invalid` 含超短样本**(「在吗」「哈哈哈哈」这些,
中位数 13 字、最短 8 字), 其余 8 个标签的文本中位数 33~35 字、**最短也有 11 字**。
于是模型学出了一个长度先验:**短文本 → 无效与恶意**。6 字的输入比训练集里任何一条都短,
完全在分布外, 输出自然是垃圾。

**修复**: 新增 269 条**短句模板**(每标签 30 条, 3~12 字, 见 `tools/_tpl_short{1,2,3}.py`),
并让 15% 的样本是**单句短文本**(`SHORT_RATIO`)。现在 9 个标签的文本最短都有 3~5 字,
"短"不再是任何标签的独有特征。修复后 `快递没到` 两个模型都能正确判成物流。

> 注: 2 字输入(如单独一个「物流」)仍在分布外 —— 训练集最短是 3 字。这属于合理边界,
> 真实工单不会只发两个字; 前端示例里特意留了一条 `快递没到` 来体现短句已经可用。
> 但要诚实说明: 这一档上两个模型的表现并不一样 —— `03-fasttext` 会输出一片低分
> (最高 `invalid` 0.067, 也就是拒识转人工, 这是对的), 而 `02-rf` 会**自信地判成**
> `invalid` 0.776。同一段分布外文本, RF 的 TF-IDF 特征会给出一个高相似度的错误落点,
> 这是纯字面特征在 OOD 输入上的固有弱点, 也是"要不要上更重的模型"的又一条证据。

**BERT 的模型要自备**: 本项目不联网下载模型。请自行把 `bert-base-chinese`
(需含 `config.json` 与权重文件)放到 `04-bert/bert-base-chinese/`, 或用环境变量
`BERT_MODEL_DIR` 指向已有目录, 然后运行 `python 04-bert/train_bert.py`。
表里 BERT 那一列是在**云端 GPU**上跑的(GPU 上取 `epochs=5`); 本机只有 CPU, 5 轮约需
20 小时, 所以 `04-bert/config.py` 里按 CPU 成本把轮数标定在 2 轮 —— 本机重训出来会低于
那一列。在模型就绪之前, 后端会自动把它标为"未就绪", 请求 BERT 时按顺序降级到其它可用
模型, 并在响应里用 `fallback_from` 说明 —— 不静默替换。

**页面上的模型选择**: `RF` / `FastText` / `BERT` / `自动` / `LLM 直连`。
「自动」= 先用默认模型, 拒识时升级 LLM 兜底; 「LLM 直连」= 完全不走本地模型(需 API Key)。
工作台的「三模型对比」会用**同一条工单**依次跑各可用模型并排展示, 这是做对照实验最直观的入口。

## 五、核心机制

**1. 双阈值拒识(不硬猜)**
9 个标签各自独立 sigmoid(不做 softmax —— 多标签不是互斥的), 然后两道闸门:
单标签激活阈值 `LABEL_THRESHOLD`(默认 0.5)与全局平均置信度 `GLOBAL_THRESHOLD`(默认 0.8)。
都不满足就**拒识**, 并给出机器可读的原因码(`no_label_activated` / `low_confidence` 等)。

> 阈值提示: 02/03 两个阶段在训练时做过阈值搜索, 最优点在 `0.3 / 0.6` 附近;
> 后端默认的 `0.5 / 0.8` 更保守(拒识更多, 更安全)。想复现训练期最优口径, 在
> `backend/.env` 里设 `LABEL_THRESHOLD=0.3`、`GLOBAL_THRESHOLD=0.6` 即可。

**2. 三级兜底链路**
本地模型 → LLM 兜底(默认**关闭**, 避免不知情地产生 API 费用) → 人工复核队列。
每一级都在响应里可见(`resolved_by` = `model` / `llm` / `human` / `none`)。

**3. 难例动态加权采样(04-bert)**
样本权重 `w = 1 + α·(标签数-1)/2 + β·漏判率 + γ·(1-平均真实标签概率)`, 默认
α=0.5 / β=1.0 / γ=0.8, 上限 5.0 —— 标签越多、越容易被漏判、模型越没把握的样本, 权重越高。

**4. 手写 LoRA(不依赖 peft)**
只注入 `query` / `value` 两个投影矩阵, `B` 全零初始化(保证训练起点等价于原模型),
冻结主干参数, 只训练 LoRA 与多标签头。参数量报告在训练日志里。

**5. 优先级是规则算出来的, 不是训出来的**
`base_priority(最急标签) × 情感系数 + 升级信号(消协/起诉/曝光等) + 多标签加分`,
≥6.0 判 P0 / ≥3.0 判 P1 / 否则 P2。规则可解释、可审计、随时可调, 比再训一个模型更划算。

**6. 话术有审批闸门**
模板生成的回复草稿在以下情况强制标记 `needs_approval=true`: P0 工单、涉及资金类标签、
命中投诉/曝光关键词、或模型结果被拒识。**模型没把握时, 话术绝不标记为可直接发送。**

## 九、常见问题

**Q: 没装 MySQL / Redis 能跑吗?**
能。会自动降级到内存存储 + 进程内限流, 页面与接口全部可用, 只是重启后数据丢失。
`/health` 和页面「系统状态」会明确标出 `storage_mode: memory` 与 `degraded: true`。

**Q: 请求 BERT 但没训练, 会报错吗?**
不会。`/models` 里它显示为"未就绪"; 真的请求它时会**按顺序降级**到可用模型, 响应里带
`fallback_from: "bert"` 说明发生了降级。三个模型都不可用时才返回 503 + 业务码 50002。

**Q: 前端为什么不用 Chart.js?**
设计文档里写的是 CDN 引入, 但这个项目要求**完全离线可用**。所以图表用 canvas 手绘
(横向柱 / 环形 / 折线, 约 120 行), 整个前端零外部依赖、零构建。

**Q: 怎么换成我自己的真实数据?**
按 `01-data/data_format.md` 的格式(`文本\t标签1,标签2`, UTF-8, `\n` 分隔)替换
`train/dev/test.txt`, 然后 `python tools/check_dataset.py` 体检, 再重训模型即可。
注意 `invalid` 必须独占, 不要与其它标签共现。

**Q: 指标为什么这么高(1.000)?**
早期版本的语料确实是这样 —— 那是**模板级泄漏**导致的假象, 不是模型强。原因和修复方式见
上文"三套对照模型"的说明。**现在 (RF 0.653 / FastText 0.760) 的数字没有这个问题**:
语料重建后 test 子句在 train 中原样出现的比例是 0.0000%。

**Q: 那 Micro-F1 只有 0.65~0.76, 是不是说明模型不行?**
不完全是。三点要看清楚:

1. **这是合成语料上的数字**, 且 train/test 的模板家族完全不重叠 —— 也就是说 test 考的是
   "没见过的说法"。真实业务语料里同一个诉求会反复以相似措辞出现, 同分布下的指标通常会
   比这个高。
2. **业务上真正该看的是"自动分流 Micro-F1 / 分流率"这一对数字**: FastText 在 83.5% 的
   工单上自动分流, 这部分准确度 0.800; 剩下 16.5% 拒识转人工/LLM。对客服场景来说,
   这个组合比一个好看的全局 F1 更有意义。
3. **两个模型的差距方向是对的**: 纯字面 n-gram 的 RF(0.653)明显弱于带词向量与
   n-gram 语义的 FastText(0.760)。这正是这张表存在的意义 —— 回答
   "我们真的需要上更重的模型吗"。

**Q: 换了数据/规模之后指标变差, 该怎么办?**
先别改模型 —— 大概率是**超参和阈值还停留在旧语料规模上**。本次重建就踩过这两个坑:

- `02-rf` 的 `max_depth=25`、`03-fasttext` 的 `epoch=1/lr=0.018` 都是给 4000 条语料调的,
  在 10 万条上分别表现为「概率被压扁」和「欠训练」;
- `tools/ml_metrics.py` 的阈值搜索原来把全局阈值候选写死在 0.6~0.9, 遇到概率尺度偏低的
  模型会**一个组合都搜不出来**, 然后静默退回默认 0.5/0.8, 跑出"拒识率 100%"这种结果。

正确做法: `python 02-rf/rf_train.py --grid-search` / `python 03-fasttext/ft_train.py --grid-search`
重选超参, 阈值搜索现在会按模型实际的置信度分布自适应生成候选。

**Q: 页面上改了模型/阈值, 会影响已落库的工单吗?**
不会。工单落库的是**当次决策的快照**(模型名、置信度、阈值结果都在里面), 之后改配置
不会回溯修改历史工单。

## 十、已知局限(诚实清单)

- **演示语料是合成的**: 模板级泄漏已修掉(见 `01-data/split_manifest.json`), 但它毕竟是
  540 条模板 + 槽位填充造出来的, 句式种类有限、没有真实的错别字/方言/多轮上下文。
  上表数字**只用于验证工程链路与三套模型的相对强弱, 不代表真实业务效果**;
  换成真实工单后需要重新跑 `--grid-search` 选超参、重新标定阈值。
- **语料规模变大后旧超参会失效**: 02-rf 的 `max_depth`、03-fasttext 的 `epoch/lr` 都已按
  10 万条语料重新用 `--grid-search` 标定过(见两个 config.py 里的说明)。换语料规模时请重跑。
- **拒识率在 dev 上标定、在 test 上会漂**: 目标 15%, FastText 在 dev 上标到 15.0%、
  test 实测 16.5%(漂 1.5 个点); RF 在 dev 上取 11.5% 时自动分流 F1 最高, test 实测
  12.1%。根因是 dev / test 各只有 108 个模板家族, 随机切分带来的难度差就足以让激活率
  从 96.6% 掉到 91.3%。真实上线必须用线上数据**持续**重标定, 不能一次标定用到底。
- **概率校准器是在 dev 上拟合的**, dev 只有 8000 条, 长尾标签(payment_account 约 770 个正例)
  的校准曲线会比较粗。真实数据上建议用更大的校准集, 或改用交叉验证拟合。
- **没有做单元测试框架**: 每个模块自带 `__main__` 自测 + 一键自检脚本, 够用但不够正式。
- **限流是固定窗口**: 实现简单可预测, 但对窗口边界的突发流量不友好(滑动窗口更准, 也更复杂)。
- **限流与缓存依赖单进程**: Redis 不可用时退化为进程内实现, 多 worker 部署时计数不共享。
- **审计日志只写不查重**: `audit_logs` 记录齐全, 但没有做定期归档与脱敏清理。
- **知识图谱只用了共现**: 目前是 9 节点的共现图 + 规则风险组合, 没有做多跳路径推理。
- **`11-ticket-kg` 的共现强度受生成语料影响**: 当前最强的共现是"售前咨询 + 其它"这类
  数据生成带来的结构, 换成真实数据后会自然变化。
- **前端未做权限分级**: 任何人都能看全部工单与看板(后端已预留 `admin_user` 依赖, 只差分工)。
- **BERT 本机未跑通端到端训练**: 表里那一列是云端 GPU 的结果(`epochs=5`), 本机只有 CPU
  且按成本把轮数标定在 2 轮, 因此**本机复现不出同一个数字**; 且该轮只落盘了单标签阈值,
  全局阈值与 ECE 没有记录。要报告里的 BERT 数字完全可复现, 需要一次固定配置的完整重训。
