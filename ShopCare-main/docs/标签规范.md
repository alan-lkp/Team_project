# ShopCare 标签规范

本文件回答三个问题: **这 9 个标签分别是什么意思、边界在哪、怎么改。**

> **唯一事实来源是 `01-data/label_meta.json` 与 `01-data/class.txt`**。
> 本文件是给**人**看的说明; 程序一律读那两个文件, 不读本文件。
> 两边不一致时以 `label_meta.json` / `class.txt` 为准(并应该把本文件改过来)。
> 阅读顺序建议: 先看「一、标签总览」, 再看「三、逐标签规范」, 需要动标签体系时直接跳到「七」。

---

## 一、标签总览

9 个标签, 顺序即索引(`class.txt` 行号 - 1), **这个顺序不要随意调整** ——
模型输出向量的第 i 维就对应第 i 个标签, 顺序变了旧模型产物就作废了。

| 索引 | 标签 | 中文名 | 责任部门 | 基础优先级 | 响应 SLA |
|:--:|---|---|---|---|---|
| 0 | `logistics` | 物流配送 | 物流仓储部 | P2 | 24 h |
| 1 | `quality` | 商品质量 | 品控/供应商 | P1 | 8 h |
| 2 | `after_sale` | 退款退货 | 售后部 | P1 | 8 h |
| 3 | `invoice` | 发票问题 | 财务部 | P2 | 24 h |
| 4 | `price_promo` | 价格与优惠 | 运营部 | P2 | 24 h |
| 5 | `payment_account` | 支付与账号 | 技术/风控 | P1 | 4 h |
| 6 | `consult` | 售前与使用咨询 | 客服中心 | P2 | 24 h |
| 7 | `service` | 服务态度 | 客服质检 | P1 | 4 h |
| 8 | `invalid` | 无效与恶意 | 风控/归档 | P2 | 72 h |

两条**硬约束**:

1. **`invalid` 是独占标签**: 命中它就意味着"这条反馈本身没有有效诉求", 因此
   它**不与其它任何标签共现**。数据里出现过 `invalid` 与其它标签同行的记录,
   `tools/check_dataset.py` 会直接报错。
2. **其余 8 类可自由组合**: 一条工单允许 1~N 个标签。真实工单里"质量差 + 要退款 +
   物流慢" 是常态, 强行归一成单标签会丢信息。

### 为什么用 9 类而不是方案文档里的 6 类

参考方案文档给的是 6 大类(物流 / 质量 / 退款售后 / 产品咨询 / 服务态度 / 无效)。
本项目在保留这 6 类语义的基础上拆出 3 类, 原因是**这 3 类的处理链路完全不同, 混在一起
会导致派单错误**:

| 拆出来的标签 | 原来混在哪 | 为什么必须独立 |
|---|---|---|
| `invoice` | 售后/其它 | 归**财务部**, 需要税号/抬头等结构化信息, 客服自己处理不了 |
| `price_promo` | 售后/咨询 | 归**运营部**, 涉及价保规则与活动配置, 需要查活动后台 |
| `payment_account` | 咨询/无效 | 涉及**资金与账号安全**, 是唯一会触发 P0 升级的类别, 必须单独识别 |

同时把方案文档里的「产品功能咨询」改名为 `consult`(售前与使用咨询)以覆盖售前问询,
`invalid` 从「无效/恶意反馈」收紧为「无效与恶意」并明确其**独占**语义。

## 二、多标签与拒识的关系(先理解这个, 再看单标签定义)

系统对一条工单的输出不是"9 选 1", 而是三个层级的判断:

```
9 个标签各自的 sigmoid 置信度
    |
    +-- 单标签阈值 LABEL_THRESHOLD (默认 0.5): 哪些标签被"激活"
    |
    +-- 全局平均置信度 GLOBAL_THRESHOLD (默认 0.8): 整体够不够可信
    |
    +-- 都不满足 -> 拒识(reject), 不给标签, 丢给人工复核队列
```

**拒识不是失败, 是设计目标。** 对"在的吗"这类任何标签都拿不准的输入, 模型的正确行为是
**承认自己拿不准**, 而不是硬塞一个标签出去 —— 后者在业务上就是错派单。

> **两种结局不要搞反**(以下均在演示语料 + 默认阈值下**实测**过):
>
> | 输入 | 实际结局 | 说明 |
> |---|---|---|
> | `随便逛逛` / `哈哈哈哈` / `1234567890` / `asdfghjkl` | **判为 `invalid`**(置信度约 1.00) | 措辞与 `invalid` 模板高度重合, 模型是**明确命中**, **不是**拒识 |
> | `在的吗` | **拒识** | 9 个标签都没过阈值 |
>
> 拒识时不同模型触发的闸门还不同, 这本身也是双阈值机制的好例子:
> `rf` 走 `low_confidence`(有一个标签 0.47, 但整体平均置信度不够),
> `fasttext` 走 `no_label_activated`(一个标签都没激活)。

> 阈值口径提示: `02-rf` / `03-fasttext` 在训练期做过阈值搜索, 最优点在 `0.3 / 0.6` 附近;
> 后端默认的 `0.5 / 0.8` 更保守。想复现训练期口径, 在 `backend/.env` 里覆盖这两个变量。

## 三、逐标签规范

每个标签给出四项: **定义** / **典型表述** / **边界(容易判错的邻近情况)** / **反例**。

### 0. `logistics` 物流配送

- **定义**: 商品已下单, 但**履约过程中**的运输、派送、签收环节出问题。
- **典型表述**: "快递在武汉停了一周了, 一直没有物流更新"; "说好次日达的, 结果五天还没送到";
  "显示已签收但东西没收到"; "快递员说放门口, 东西到现在没看到"; "想改一下收货地址, 还没派送"。
- **边界**:
  - 「发货慢」算 `logistics`(商家履约), 但「下单后不想买了想取消」算 `after_sale`;
  - 「外包装破损」若**只**抱怨包装算 `logistics`, 若**已经影响商品**再加 `quality`;
  - 「快递员态度差」算 `logistics`, 若是**商家客服**态度差则算 `service`。
- **反例**: "优惠券用不了"(→ `price_promo`)、"我要退款"(→ `after_sale`)、
  "你们家快递费怎么收"(→ `consult`)。

### 1. `quality` 商品质量

- **定义**: **商品本身**存在缺陷、与描述不符、或功能异常。
- **典型表述**: "收到的电饭锅是坏的"; "面料和图片完全不一样, 做工粗糙"; "用了两天就出故障";
  "少发了一个配件"; "已经过期了"; "尺码严重偏小"; "电池不耐用"。
- **边界**:
  - 「实物与描述不一致」算 `quality`; 「活动页面说买一送一但没送」算 `price_promo`
    (这是**承诺未兑现**, 不是商品缺陷);
  - 「刚拆开就发现屏幕有裂纹」—— 只有这一句时倾向 `quality`(缺陷已存在于商品),
    若能明确是运输导致, 可同时给 `logistics`;
  - 「味道刺鼻」若指商品本身 → `quality`; 若指快递包装 → `logistics`。
- **反例**: "客服一直敷衍我"(→ `service`)、"我要退货"(→ `after_sale`)。

### 2. `after_sale` 退款退货

- **定义**: 用户**明确提出**售后诉求 —— 退款、退货、换货、维修, 或**已发起**的售后流程卡住/异常。
- **典型表述**: "我要退款"; "申请退货好几天了没人处理"; "退款一周了还没到账";
  "想换成大一码的, 怎么走换货流程"; "保修期内怎么维修"; "运费谁承担"。
- **边界**:
  - **与 `quality` 的分工**: `quality` 描述"东西有问题"(事实), `after_sale` 描述
    "我要处理"(诉求)。"收到的锅是坏的" → `quality`; "锅是坏的, 我要退款" → `quality,after_sale`;
  - **与 `payment_account` 的分工**: "退款没到账"通常是 `after_sale`(售后流程问题);
    但如果是**支付通道异常**(钱扣了订单没生成、重复扣款)则归 `payment_account`;
  - 尚未购买的"想问下退货规则"算 `consult`, **不算** `after_sale`。
- **反例**: "这款支持无线充电吗"(→ `consult`)、"发票怎么重开"(→ `invoice`)。

### 3. `invoice` 发票问题

- **定义**: 与**开票本身**相关的诉求 —— 申请开票、发票信息错误、重开、作废、未收到发票。
- **典型表述**: "买完想开个发票在哪里申请"; "发票抬头写错了能重开吗"; "订单完成了发票一直没收到";
  "电子发票下载不了"; "发票金额对不上"; "报销要用, 麻烦尽快开"; "想开公司抬头的专票"。
- **边界**:
  - 「发票金额不对」若同时涉及**优惠没给**, 应给 `invoice,price_promo`;
  - 「发票没收到」是 `invoice`(单据未达), 不要误判成 `logistics`(那是商品运输);
  - 「开票流程太麻烦, 客服也不教」—— 主诉是开票 → `invoice`, 若抱怨客服态度再加 `service`。
- **反例**: "我要退款"(→ `after_sale`)、"这款有货吗"(→ `consult`)。

### 4. `price_promo` 价格与优惠

- **定义**: 与**价格、优惠、活动、赠品**相关 —— 价保、券生效、满减、折扣、多扣款、赠品未发。
- **典型表述**: "刚买完就降价了, 能补差价吗"; "券显示可用结算又用不了"; "说好的满减没减";
  "秒杀价付款时变回原价"; "会员折扣没生效"; "赠品没发"; "多扣了我一笔钱"。
- **边界**:
  - 「多扣款」若已经属于**重复扣款/支付异常**, 优先 `payment_account`, 可叠加 `price_promo`;
  - 「承诺买一送一没送」算 `price_promo`(营销承诺), 不算 `quality`;
  - 纯咨询「买两件有没有优惠」→ `consult`(还没买), 不算 `price_promo`。
- **反例**: "质量太差了"(→ `quality`)、"发票重开"(→ `invoice`)。

### 5. `payment_account` 支付与账号

- **定义**: **资金安全与账号访问**层面的问题 —— 支付失败、重复扣款、订单状态异常、账号封禁/盗用/登录异常。
- **典型表述**: "付款一直失败, 换了好几张卡都不行"; "钱扣了但订单显示未支付";
  "莫名其妙被扣了两次款"; "账号登不上去了"; "账号被冻结"; "账号被盗, 有笔不是我下的单";
  "想改绑手机号收不到验证码"。
- **边界**:
  - 「订单一直显示待支付但我付过了」→ `payment_account`(支付状态不一致);
  - 「退款没到账」→ `after_sale`(售后流程), 除非明确是**支付通道**问题;
  - 这类问题**天然高风险**, 优先级引擎会额外加权, 并可能触发 P0 升级与「必须人工审批」
    的话术闸门 —— 详见 `09-priority/` 与 `10-reply-recommend/`。
- **反例**: "物流太慢了"(→ `logistics`)、"这块石头真好看"(→ `invalid`)。

### 6. `consult` 售前与使用咨询

- **定义**: **尚未产生纠纷**的正常问询 —— 商品参数、适配性、使用方法、安装、库存时效、规则确认。
- **典型表述**: "这款支持无线充电吗"; "尺寸是多少"; "现在有货吗, 多久能发";
  "怎么安装, 有教程吗"; "适合三岁小孩用吗"; "保修期多久"; "怎么连蓝牙, 说明书看不懂";
  "能带上飞机吗"; "想问下退货规则, 先了解一下"。
- **边界**:
  - 「保修期多久」→ `consult`(咨询规则); 「坏了要维修」→ `after_sale`(发起诉求);
  - 「想问下优惠怎么算」(未购买) → `consult`; 「我买的时候有券但没减」(已购买且受损) → `price_promo`;
  - `consult` 与 `invalid` 最容易混: 有具体问句的是 `consult`, 纯灌水/符号/字符乱打的是 `invalid`。
- **反例**: "哈哈哈哈哈哈"(→ `invalid`)、"我要投诉到底"(→ `service` / `invalid`)。

### 7. `service` 服务态度

- **定义**: 投诉**客服服务质量** —— 回复慢、态度差、敷衍、推诿、承诺不兑现、转接无果。
- **典型表述**: "客服半天不回消息, 问了三遍没人理"; "客服态度特别差, 说话很不客气";
  "转接了四个客服问题还没解决"; "一直敷衍我, 让我自己看规则";
  "承诺24小时回复但没人联系我"; "把责任推给快递"; "机器人客服绕来绕去转不到人工"。
- **边界**:
  - 投诉对象必须是**人的服务**; 投诉**商品** → `quality`, 投诉**系统** → 通常是 `service` 或 `invalid`;
  - 「答应给我补发, 结果一直没动静」是**承诺未兑现** → `service`(可叠加 `after_sale`);
  - 只是"联系不上客服"本身可能同时意味着售后卡住, 视上下文叠加 `after_sale`。
- **反例**: "东西坏了"(→ `quality`)、"快递员不送上楼"(→ `logistics`)。

### 8. `invalid` 无效与恶意(独占)

- **定义**: 这条反馈**不携带可处理的有效诉求** —— 灌水、纯符号、乱码、广告、刷单、
  与商品无关的内容、恶意差评威胁、辱骂。
- **典型表述**: "哈哈哈哈哈哈哈哈"; "在吗"; "测试测试测试"; "???"; "1234567890";
  "asdfghjkl"; "加我微信可以领内部优惠"; "刷单了解一下, 需要的私聊";
  "随便点几下看看"; "别买, 都是骗人的, 我已经举报了"。
- **边界(最重要)**:
  - 「买它买它买它, 五星好评好评好评」—— 看似正面, 但**没有诉求** → `invalid`;
  - 「发错了吧, 我没买过这个东西啊」—— 表面上像物流/订单问题, 但属于**无有效诉求的错发反馈**,
    这是经典歧义样本, 标注时**需要看原工单上下文**, 语料里刻意保留了这类边界;
  - 「你们系统真烂, 我要投诉到底, 天天投诉」—— 纯情绪宣泄、无具体事由 → `invalid`;
    若能指出**具体是哪件事**导致不满, 则按事由给标签(如 `service`)。
- **反例**: "这款有货吗"(→ `consult`)、"我要退款"(→ `after_sale`)。

**风险组合(规则, 见 `11-ticket-kg/ticket_kg.py` 的 `RISK_COMBOS`)**:

| 组合 | 等级 | 说明 |
|---|---|---|
| `payment_account` + `after_sale` | **P0** | 资金问题叠加退款诉求, 极易升级为投诉/资金争议, 需主管介入并留痕 |
| `payment_account` | P1 | 涉及资金, 需核对流水后再回复, 不能让客服口头承诺到账时间 |
| `quality` + `after_sale` + `service` | P1 | 质量+售后+服务三连, 典型差评/曝光前兆 |

## 五、随标签一起输出的两个衍生维度

标签不是全部输出。同一个工单还会带上**情感**与**优先级**, 两者的规则也定义在
`label_meta.json` 里(与标签共用一份配置)。

### 5.1 情感极性(3 类)

| 值 | 中文 | 优先级系数 | 说明 |
|---|---|---|---|
| `positive` | 正面 | 0.5 | 表扬、满意。**会调低**优先级 |
| `neutral` | 中性 | 1.0 | 客观陈述、纯问询 |
| `negative` | 负面 | 2.0 | 不满、抱怨、愤怒。**会调高**优先级 |

由 `08-sentiment/sentiment_classifier.py` 的**词典 + 规则**产出(**不是训练出来的**),
并可被情感词、程度副词、否定词与感叹号数量调制。

### 5.2 优先级(3 档)

| 值 | 中文 | SLA |
|---|---|---|
| `P0` | 紧急 | 1 h |
| `P1` | 高 | 4 h |
| `P2` | 常规 | 24 h |

计算方式(见 `09-priority/priority_engine.py`):

```
分数 = 基础优先级(取最急的那个标签) x 情感系数 + 升级信号 + 多标签加分
分数 >= 6.0 -> P0      分数 >= 3.0 -> P1      否则 -> P2
```

**升级信号**是关键词命中的, 例如提到消协/12315/起诉/媒体曝光/律师/报警这类词会显著加分 ——
它们代表"这个工单可能不只停在线上了"。**规则可解释、可审计、随时可调**, 比再训一个模型划算。

## 六、标注规范

如果你要拿这套体系去标**真实工单**, 建议按下面的约定来, 否则数据进模型前会先炸在
`tools/check_dataset.py` 上。

### 6.1 最小标注单元

**一行 = 一条工单 = 用户的一次完整诉求**。不要把一次对话的多条消息拆成多行, 也不要把
多个用户的反馈合成一行。

### 6.2 标注顺序

1. **先判 `invalid`**: 这条反馈有没有可处理的有效诉求? 没有就直接 `invalid`, **结束**
   (不要再给别的标签)。
2. **再判事实类**: `logistics` / `quality` / `invoice` / `price_promo` / `payment_account`
   —— 描述"发生了什么"。
3. **再判诉求类**: `after_sale` —— 描述"用户要什么"。
4. **最后判咨询与服务**: `consult`(正常问询) / `service`(投诉服务)。

### 6.3 三条纪律

| 纪律 | 说明 |
|---|---|
| **宁缺毋滥** | 标签必须是**文本明确支持**的。靠脑补推测出来的标签会污染训练集, 比漏标更有害 |
| **不重复语义** | 同一件事不要挂两个同义标签。比如"东西坏了要退"是 `quality,after_sale`, 不是 `quality,quality` |
| **`invalid` 独占** | 给了 `invalid` 就不能给其它标签, 数据校验会强制检查 |

### 6.4 歧义样本怎么办

留**多人标注 + 仲裁**: 同一个 batch 由 2 人独立标, 不一致的挑出来讨论定标。
本项目演示语料里刻意保留了少量歧义样本(如"发错了吧, 我没买过这个东西啊"), 就是为了
让这套流程有东西可练。

### 6.5 一致性指标

真实标注项目建议统计 **Krippendorff's alpha**(多标签可用其名义尺度变体), 经验阈值:

| alpha | 解读 |
|---|---|
| < 0.60 | 标注规范有歧义, 回去改规范, 不要急着训模型 |
| 0.60 ~ 0.80 | 可用, 但需要对分歧标签做专项澄清 |
| > 0.80 | 标注质量良好 |

### 6.6 提交前自检

```bash
python tools/check_dataset.py            # 格式 / 标签合法性 / invalid 独占 / 分布 / 长度
python 01-data/data_eda.py               # 分布 / 共现矩阵 / 长度分位 / 重复检测
```

`check_dataset.py` 还会拒绝: 空行、未知标签、`invalid` 与其它标签共现、超长文本、重复文本。

## 七、怎么改标签体系

**改动面很小, 但要改全**。标签是"配置", 不是"代码", 所以只要改下面这几处。

### 7.1 新增一个标签(以新增 `coupon` 为例)

| 步骤 | 文件 | 做什么 |
|:--:|---|---|
| 1 | `01-data/class.txt` | 在末尾**追加**一行 `coupon`(**不要插在中间**, 否则旧模型产物全部作废) |
| 2 | `01-data/label_meta.json` | 在 `labels` 下加一项: `cn` / `dept` / `base_priority` / `sla_hours` / `desc` |
| 3 | `tools/generate_ticket_data.py` | 在 `LABEL_TEMPLATES` 里加该类模板(否则重新生成的数据里没有这个标签) |
| 4 | 语料 | 在 `train/dev/test.txt` 补样本, 或重跑生成脚本 |
| 5 | —— | 重新训练三个模型(RF / FastText / BERT), 旧产物无法识别新标签 |
| 6 | `frontend/web/js/app.js` | 前端标签名与图例读的是 `/labels` 接口, **通常不用改**; 只有硬编码的示例文本需要顺带更新 |

### 7.2 重新生成数据后

```bash
python tools/generate_ticket_data.py     # 重新生成 train/dev/test
python tools/check_dataset.py            # 体检
python 01-data/data_eda.py               # 看新分布与共现
python 02-rf/rf_train.py                 # 重训(03/04 同理)
python tools/verify_all_phases.py        # 一键自检
```

### 7.3 会被标签体系**自动**影响的下游

改完 `class.txt` + `label_meta.json` 后, 下面这些**不用改代码**就会跟着变:

- 后端 `/labels` 接口返回的中文名、部门、SLA;
- 优先级引擎的基础优先级取值;
- 话术模板里的部门署名与处理承诺;
- 前端工作台的标签中文名与看板图例;
- 知识图谱的节点集合与共现统计。

### 7.4 不要做的事

| 不要 | 原因 |
|---|---|
| 调整 `class.txt` 的**行序** | 索引即标签 id, 顺序变了旧模型全部作废 |
| 让 `invalid` 与其它标签共现 | 语义冲突, 校验会拦 |
| 只改代码不补语料 | 新标签没有训练样本, 模型学不到 |
| 只改语料不重训 | 模型对旧标签体系有记忆, 改数据不会自动生效 |
