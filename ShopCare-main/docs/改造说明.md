# ShopCare 改造说明

本文件说明 `ShopCare-main` 是**怎么从 `szai8_tmf_project` 改过来的** ——
保留了哪些设计、换了哪些东西、为什么换, 以及后续要接着做什么。

**一句话总结**: 保留原项目"三套对照模型 + 逐阶段递进"的教学骨架, 把任务从
**10 类新闻单标签分类**改造成 **9 类电商客服工单多标签分类**, 把每个阶段各自一份的
Flask 巨型脚本收拢成**一个 FastAPI 服务**, 并在分类之上补上业务闭环所需的四个模块
(情感 / 优先级 / 话术 / 知识图谱)。

---

## 一、源项目概况

`szai8_tmf_project` 是一个中文新闻(TNEWS 类)文本分类教学项目, 特点是**按阶段递进**:
每个阶段一个独立目录, 编号越大技术越新, 一路从传统机器学习走到模型压缩。

| 源目录 | 内容 |
|---|---|
| `_01_data/` | 新闻语料 train/dev/test + 10 类 `class.txt` |
| `_02_rf/` | 分词 → TF-IDF → 随机森林 训练/评估/推理 + Flask/FastAPI 部署 |
| `_03_fasttext/` | 字符级与词级两种处理方式、默认参数与自动调参 + 部署 |
| `_04_bert/` | BERT 分类模型、CPU/GPU 训练、评估、推理 + 部署 |
| `_05_llm/` | 调用 DeepSeek / 智谱 / 百炼 API 做分类, 与系统提示词评估 |
| `_06_bert_quantization/` | BERT 动态量化 |
| `_07_bert_distillation/` | BERT 蒸馏到 BiLSTM |
| `_08_bert_pruning/` | BERT 全局非结构化剪枝 |
| `00_test/` | 各种语法与 API 的小 demo(RNN/LSTM/GRU、Embedding、张量运算等) |

**源项目的数据格式**: 每行 `文本 \t 类别索引`(单标签, 数字索引)。

**源项目的部署方式**: `_02_rf/_06_基于flask的web部署.py` 这类脚本, 每个阶段一份,
每份约 21 KB, 自己起一个端口、自己读自己的模型、自己渲染 HTML —— 阶段之间无法共存,
也无法组合使用。

## 三、七项关键改造

### 改造 1: 单标签 → 多标签(最根本的一项)

| | 源项目 | 本项目 |
|---|---|---|
| 任务 | 10 选 1(互斥) | 9 个标签自由组合(不互斥) |
| 输出层 | softmax(概率和为 1) | **9 个独立 sigmoid**(各自判定) |
| 损失函数 | CrossEntropy | BCEWithLogits(带 `pos_weight` 处理不均衡) |
| 数据标签 | `3`(一个索引) | `quality,after_sale`(逗号连接的多个标签) |
| 随机森林 | 单输出分类器 | **OneVsRest**(每类一个二分类器) |
| FastText | 默认 `softmax` | **`loss='ova'`** |

**为什么必须改**: 真实工单天然多诉求。"快递五天没到 + 客服不回消息 + 我要退款" 这条
文本用单标签模型只能三选一, 剩下两个诉求直接丢失 —— 后续派单就会漏部门。
这一点在参考方案文档里也是核心论点("工业客服工单真实落地主流方案, 优于传统单标签")。

### 改造 2: 标签体系 10 类新闻 → 9 类电商

源项目的 `finance / realty / stocks / education / science / society / politics / sports /
game / entertainment` 与客服场景完全无关, 整体替换为电商工单的 9 类。
标签的选取理由、逐类边界与反例见 `docs/标签规范.md`, 这里只说改造思路:

- 以参考方案文档的 **6 大类**为语义基线(物流 / 质量 / 退款售后 / 产品咨询 / 服务态度 / 无效);
- 拆出 3 个**处理链路完全不同**的类别(`invoice` / `price_promo` / `payment_account`) ——
  它们分别归财务部、运营部、技术风控, 混在"售后"里必然派错单;
- 明确 `invalid` 为**独占标签**(源项目没有这个约束, 因为单标签天然独占)。

### 改造 3: 标签元数据集中到一份文件

源项目里"类别名"只有 `class.txt` 一份, 但**类别的中文名、归属部门、优先级**散落在
各阶段的注释与部署脚本里。本项目新建 `01-data/label_meta.json`, 把

```json
{"logistics": {"cn": "物流配送", "dept": "物流仓储部",
               "base_priority": "P2", "sla_hours": 24, "desc": "..."}}
```

作为**全项目唯一事实来源**。后端 `/labels` 接口、优先级引擎、话术模板、前端标签图例、
知识图谱节点全部读它 —— 改标签只需要改这一个文件加 `class.txt`, 不会出现
"后端说是物流部、话术里写着仓储部"这种不一致。

### 改造 4: 各阶段各自的 Flask 脚本 → 一个 FastAPI 服务

源项目每个阶段一份约 21 KB 的部署脚本, 各自硬编码模型路径、各自渲染 HTML, 结果是:

- 同一台机器上**只能跑一个阶段**(端口与 HTML 都冲突);
- 三个模型的结果**格式各不相同**, 想横向对比得人工对齐字段;
- 没有认证、没有限流、没有错误码规范。

本项目改为**一个 FastAPI 服务**, 并在 `tools/ticket_predictor.py` 里定义**统一返回契约**
(`RESULT_KEYS`), 让三个模型的推理函数必须返回同一组字段:

```
labels / confidences / top_k_scores / rejected / reject_reason /
model_name / elapsed_ms / ...
```

前端的「三模型对比」就是靠这个契约, 才能用同一条工单依次跑各模型并排展示。

服务本身按职责分层:

| 层 | 目录 | 职责 |
|---|---|---|
| 配置 | `backend/common/config.py` | 所有环境变量集中在 `Settings` |
| 存储 | `backend/common/store.py` | MySQL / Redis / 内存三级降级 |
| 模型 | `backend/common/model_registry.py` | 隔离加载三套 `config.py`, 懒加载 + 自动降级 |
| 编排 | `backend/common/pipeline.py` | 把 模型→情感→优先级→话术→图谱 串成一次 `analyze()` |
| 路由 | `backend/api/` | user / model / classify / ticket / dashboard 五组 |
| 中间件 | `backend/middleware/context.py` | 请求 ID / 限流 / 访问日志 |

> **`config.py` 同名冲突是个真问题**: `02-rf`/`03-fasttext`/`04-bert` 都叫 `config.py`,
> 同一个 Python 进程里先后 import 会命中 `sys.modules` 缓存拿到第一个。源项目没有这个问题
> (因为它不组合使用), 但本项目必须在**一个进程里同时持有三个模型配置**, 所以
> `model_registry.py` 用 `importlib` 把三份配置注册成
> `_shopcare_02_rf_config` / `_shopcare_03_ft_config` / `_shopcare_04_bert_config`
> 三个互不相同的模块名。自检脚本也据此让每个阶段跑在独立子进程里。

### 改造 5: 从"只有分类"到"决策闭环"

源项目的输出止于"这条文本属于哪一类"。但客服场景真正要的是**可派单的决策**。本项目在
分类之上补了四个模块:

| 模块 | 输入 | 输出 | 为什么需要 |
|---|---|---|---|
| `08-sentiment` | 文本 | positive / neutral / negative | 优先级要区分"问一句"和"骂着问" |
| `09-priority` | 标签 + 情感 | P0/P1/P2 + SLA + 是否需复核 | 客服要按紧急度排队 |
| `10-reply-recommend` | 标签 + 优先级 | 回复草稿 + `needs_approval` | 提升响应速度, 但资金类必须人工把关 |
| `11-ticket-kg` | 标签组合 | 召回补全 + 风险预警 + 根因方向 | 从"贴标签"到"提示下一步查什么" |

**这四个模块都不是训出来的, 全是规则** —— 优先级规则可解释、可审计、随时可调,
比再训一个模型划算得多。LLM 兜底同理: 源项目把 LLM 当作独立的分类方案, 本项目把它
降级为**拒识后的第三级兜底**, 且**默认关闭**(避免不知情地产生 API 费用)。

### 改造 6: 补齐工程化设施

源项目是教学项目, 缺少上生产需要的东西。本项目新增:

| 设施 | 位置 | 说明 |
|---|---|---|
| 统一响应结构 | `backend/common/shop_utils.py` | `{"code":0,"message":"ok","data":{...}}` + 业务码 |
| JWT 认证 | `backend/common/security.py`, `backend/api/deps.py` | 注册/登录/登出 + jti 黑名单 |
| 密码哈希 | `backend/common/security.py` | PBKDF2-SHA256 + 随机盐(不存明文) |
| 限流 | `backend/middleware/context.py` | 固定窗口, Redis 优先, 进程内兜底 |
| 降级与暴露 | 全项目 | 连不上就降级, **但必须在 `/health` 里如实显示**, 不静默替换 |
| 数据体检 | `tools/check_dataset.py` | 格式 / 标签合法性 / `invalid` 独占 / 分布 / 长度 |
| 一键自检 | `tools/verify_all_phases.py` | 各阶段自测 + 端到端接口自测(23 步) |
| 环境变量 | `backend/.env.example` | 主机/账号/密钥全部走环境变量, 不硬编码 |

### 改造 7: 训练侧的三点保留与强化

源项目在 BERT 阶段做了量化 / 蒸馏 / 剪枝。本项目**保留了这条进阶路线**(目录占位),
但在 BERT 训练阶段先把三件更影响落地效果的事做扎实:

| 能力 | 位置 | 说明 |
|---|---|---|
| 手写 LoRA | `04-bert/lora_utils.py` | 只注入 `query`/`value`, `B` 零初始化; 不依赖 `peft` |
| 难例动态加权采样 | `04-bert/hard_example_sampler.py` | 样本权重按标签数 / 漏判率 / 置信度缺口动态调整, 上限 5.0 |
| 双阈值拒识 | `04-bert/reject_utils.py` | 单标签阈值 + 全局平均置信度, 不满足则拒识并给出原因码 |

> **源项目的"拒识"是隐含的**(softmax 取最大值, 永远有答案); 本项目把它显式化为一个
> **可配置、可评估、会在响应里说明原因的**机制。这是从"教学"到"落地"最关键的一步 ——
> 一个永远给答案的模型在业务上是危险的。

## 五、改造中踩到的坑(给后来人)

| 坑 | 现象 | 处理 |
|---|---|---|
| **`config.py` 同名** | 同进程里 import 两个阶段的 `config`, 拿到的是第一个 | 每个阶段跑子进程; 后端用 `importlib` 注册唯一模块名 |
| **全角逗号** | 人工标注时用了中文 `，`, 一个标签被当成"未知标签" | `tools/ticket_data.py` 的 `LABEL_SEP` 兼容中英文逗号 |
| **CRLF 换行** | Windows 下 `\r\n` 会让每行最后一个标签带上 `\r` | 读取时 `rstrip('\r')`; 生成数据时强制写 `\n` |
| **`invalid` 被共现** | 生成器若不做约束, 会出现 `invalid,consult` 这种行 | 生成时独占; 校验脚本强制拦截 |
| **模型加载慢** | 首次请求约 7 s | 懒加载 + 进程内缓存(不是卡死); `/health` 里能看到模型就绪状态 |
| **模板级泄漏** | 演示语料上 Micro-F1 = 1.000: 整句查重是 0, 但 test 里 96.6% 的子句能在 train 中原样找到 | 用 `tools/build_dataset_v2.py` 重建语料(540 条模板 + 家族分组切分 + 槽位隔离), test 子句覆盖率降到 0.0000%; 详见 README「三套对照模型」 |
| **阈值搜索写死候选** | RF 上跑出"拒识率 100%、自动分流率 0%" | `tools/ml_metrics.py` 的全局阈值候选原来写死 0.6~0.9, 概率尺度偏低的模型一个组合都搜不出来, 于是静默退回默认阈值。改成按模型实际置信度分布自适应生成 |
| **超参停留在旧语料规模** | FastText dev Micro-F1 只有 0.17、预测标签数是真实的 1.8 倍 | `epoch=1/lr=0.018`、`max_depth=25` 都是给 4000 条语料调的。两个 config.py 已按 10 万条重跑 `--grid-search` 并写明来源 |
| **置信度不可比 / 显示 100%** | 同一条工单: RF 显示 60.5%(像模型没把握)、FastText 显示 100.0%(像数据泄漏) | 两个模型的**原始概率尺度**本来就不同, 而且错的方向相反: RF 的树投票概率整段被压在 `[0.041, 0.799]`(它说 0.259 时实际只有 2.6% 命中), FastText 的 ova sigmoid 会饱和(7.40% 的标签正好顶到 1.000, 而 0.9~0.999 那档只说对 67.1%)。新增 `tools/prob_calibration.py`, 在 dev 上逐标签拟合单调映射, 两端都过一遍 —— test 上 ECE 从 **0.197/0.054 降到 0.020/0.016**。FastText 用 Platt, RF 用**等频分箱**(RF 的有效信息集中在 `[0.6, 0.8]` 这一小段, Platt 这条全局 sigmoid 到高分段就变成从个位数样本外推), 详见 README「4.1 概率校准」 |
| **"9 类置信度分布"永远只有 1 条柱子** | 标题写"含未激活, 可看出模型在犹豫什么", 实际那 8 条永远是空槽 | 接口只透出了 `confidences`(仅含**被激活**的标签), 未激活的一律缺失。已新增 `all_scores` 字段透出全部 9 类, 前端改用它渲染 |
| **fasttext 批量 predict 有坑** | 传列表且 k>1 时, 会把 top-1 的概率广播给全部 k 个标签 | 本项目所有调用点都是逐条传字符串, 不受影响; 已在 `ft_predict_fun.py` 注释里写明, 避免后来人改成批量 |
| **长度先验** | 「快递一直没到」(6 字)判成 `invalid` 1.00; 而「我的快递一直没到」(8 字)正确判成物流 | 语料里 9 个标签只有 `invalid` 含超短样本(中位 13 字), 其余中位 33~35 字、最短 11 字 —— 模型学出了「短文本 → 无效与恶意」。新增 269 条短句模板 + 15% 单句短样本(`SHORT_RATIO`), 详见 README「4.2 长度先验」 |
| **重训后缓存不失效** | 页面右上角一直显示"命中缓存", 看起来像新模型没生效 | `cache_key` 只含文本+模型名+阈值, **没有模型版本**。已加模型指纹(训练时间 + 模型文件 mtime/大小), 模型一被覆盖缓存键就变, 不需要手动清缓存 |
| **04-bert 与另两套模型口径不一致** | 三套模型的置信度/拒识率没法放一张表比 | BERT 这边漏了三件事: ① 推理结果没有 `all_scores` 字段(前端 9 类分布画不出来, backend 字段自检也会挂); ② 完全不参与概率校准; ③ 训练端不标定阈值(固定 0.5/0.8), 而且推理端**从不读产物里的阈值**。已全部补齐, 三套模型现在共用 `tools/prob_calibration.py` 与 `tools/ml_metrics.grid_search_thresholds` |
| **`04-bert/reject_utils.py` 有重复实现** | 那份 `grid_search_thresholds` 全局候选写死 0.6~0.9 | 是死代码(从没被调用过), 且带着和 RF 同款的坑。已删除, 统一走 `tools/ml_metrics.py` |
| **`--lr` 是哑参数** | `train_bert.py --lr 5e-5` 传了没反应 | 写的是 `cfg.lr = args.lr`, 但 config 里没有 `lr` 字段(优化器读的是 `cfg.learning_rate`)。已改为 `cfg.learning_rate` |
| **默认密钥上线** | `JWT_SECRET` 仍是 `dev-secret-change-me` | `/health` 主动告警, 提醒替换 |
